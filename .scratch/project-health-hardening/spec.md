# 个人资产看板：项目健康度与分阶段优化规格

Status: ready-for-agent
Review date: 2026-09-10
Scope: 既有项目的可靠性、安全、性能与工程可维护性

> 本次只发布规格和独立 Ticket，不修改业务代码、不提交、不推送。ready-for-agent 表示规格已整理，不代表所有者已经确认实施；执行任何代码变更前仍需取得其确认。

## Problem Statement

系统性审查的整体健康度为 **6.5/10**。项目已有明确的单所有者、只读来源和领域语义，也有类型检查及多层测试，但数据恢复完整性、认证挑战生命周期与独立任务入口存在确定问题；默认质量门禁未覆盖全部已有测试。评分是审查判断，不是覆盖率或线上稳定性指标。

最重要的三个问题：

1. **备份恢复丢失业务事实**：手工资产记录与正式日结没有进入备份载荷，恢复删除原数据后无法回填。
2. **Passkey 挑战可重放**：缺少服务端单次消费与时效约束，合法零计数器断言可重复通过验证。
3. **正式日结 CLI 无法启动**：Node ESM 无法解析间接导入的 Next headers 子路径，业务执行前就退出。

另有严重依赖公告命中，须立即核对暴露条件并定向修复；现有证据不能证明当前部署可被利用。

## Solution

将问题拆为 11 个独立 Ticket，先修复数据安全、认证和任务入口，同时补齐低成本质量门禁；再减少历史读取与活动请求浪费、修复键盘交互；最后处理生产模块拆分及原生构建生命周期。每个 Ticket 包含位置、原因、影响、最小方案、风险、收益和可观察验收。

执行优先级兼顾严重性和投入：备份、挑战及严重公告处置应立即启动；测试收集、CLI 导入和版本声明适合作为可独立交付的小改动，不成为前述安全修复的强制前置。大规模重构不与行为修复混在一次变更中。

## User Stories

1. 作为所有者，我希望备份包含全部业务历史，以便恢复设备后仍能查看原有资产事实。
2. 作为所有者，我希望手工资产记录的日期和原始币种完整恢复，以便继续编辑与删除记录。
3. 作为所有者，我希望删除最新手工记录后回退到上一条，以便当前总额保持既有语义。
4. 作为所有者，我希望正式日结及其来源、持仓证据完整保留，以便审查历史市场交易日与采集窗口。
5. 作为所有者，我希望历史金额与历史汇率不被当前行情改写，以便恢复前后结果一致。
6. 作为所有者，我希望恢复预演展示完整替换范围，以便在确认前识别数据损失。
7. 作为所有者，我希望旧备份缺失的数据域得到明确提示，以便不会在不知情时丢弃现有历史。
8. 作为所有者，我希望非法或损坏备份在覆盖前被拒绝，以便现有数据保持可用。
9. 作为所有者，我希望恢复失败可以回滚且重复恢复不产生重复事实，以便可靠重试。
10. 作为所有者，我希望备份不包含任何授权秘密，以便业务数据迁移不泄漏凭证。
11. 作为所有者，我希望自动来源恢复后保持断开，以便重新授权前不会访问平台。
12. 作为所有者，我希望登录与预置挑战只可使用一次，以便截获的旧响应不能再次建立会话。
13. 作为所有者，我希望过期和用途不符的挑战被拒绝，以便认证边界不依赖浏览器 Cookie 行为。
14. 作为所有者，我希望合法零计数器 Passkey 仍可使用，以便安全修复不破坏设备兼容性。
15. 作为所有者，我希望多标签页重新登录时有明确反馈，以便不会误解失效挑战。
16. 作为所有者，我希望 HTTPS 会话 Cookie 有合适传输约束，以便会话凭证受到保护。
17. 作为所有者，我希望 TOTP 一次性计数器和限流继续有效，以便备用登录不被回归破坏。
18. 作为所有者，我希望正式日结独立任务能够正常启动，以便定时任务进入正确的采集流程。
19. 作为维护者，我希望 CLI 启动测试不依赖真实账户，以便安全复现导入和退出行为。
20. 作为维护者，我希望默认测试执行所有约定的单元测试，以便已有防线不会因清单遗漏失效。
21. 作为维护者，我希望 smoke 与完整回归的范围清楚，以便不把局部通过当作全面验收。
22. 作为所有者，我希望严重依赖公告得到逐项处置，以便知道实际暴露条件和剩余风险。
23. 作为维护者，我希望升级限制在必要依赖，以便减少框架和传递依赖兼容性回归。
24. 作为所有者，我希望长期历史增长后单日更新仍轻量，以便日常操作不读取不相关的多年数据。
25. 作为所有者，我希望来源详情只读取所选来源和区间，以便页面工作量与当前需求匹配。
26. 作为所有者，我希望趋势的空日期与不完整观测保持原样，以便性能优化不会美化或伪造历史。
27. 作为所有者，我希望连续输入合并会话活动通知，以便减少重复请求而不被误锁。
28. 作为所有者，我希望停止操作后按既定期限锁定，以便减少请求不会降低空闲保护。
29. 作为键盘操作的所有者，我希望 Enter 执行实际聚焦的按钮，以便不会误触其他命令。
30. 作为使用中文输入法的所有者，我希望组合输入不执行菜单命令，以便顺畅输入搜索内容。
31. 作为维护者，我希望生产装配和持久化职责清楚，以便未来变更可在小范围内验证。
32. 作为维护者，我希望已有原生产物的启动不再隐式编译，以便运行环境不被构建工具链阻塞。
33. 作为维护者，我希望不兼容原生产物尽早明确失败，以便不会使用错误架构或泄漏秘密的替代路径。
34. 作为维护者，我希望运行时和包管理器版本经过验证并有声明，以便可复现安装与任务启动。
35. 作为所有者，我希望本次只得到可审阅规格，以便确认最小改动范围后再实施。
36. 作为所有者，我希望确定问题与待验证项分开记录，以便优化决策建立在真实证据上。

## Implementation Decisions

- 保持单所有者、无公开注册、无交易与转账能力；演示模式只使用进程内虚构数据，不读写所有者服务或存储。
- 备份模块覆盖全部持久业务数据域，认证秘密继续隔离；通过版本升级、明确旧版缺失策略与事务恢复保证完整性。
- 认证模块增加服务端签发、时效、用途绑定和原子消费；保留现有验证器与零计数器兼容，不替换成只靠计数器的防护。
- 正式日结任务先以最小导入修复恢复可启动性，保持日结采集和不可变证据口径；没有采集的数据不能由后续行情补造。
- 查询端口先支持单日直接读取，再支持来源/日期范围与批量子记录组合；全量导出保留完整读取路径。
- 会话守卫合并通知但不改变真实活动判定和服务端空闲边界；命令菜单按输入焦点区分搜索快捷键与按钮原生行为。
- 生产模块按职责渐进拆分，先维持公开接口与初始化语义；原生扩展在构建阶段准备，启动阶段检查兼容性。
- 当日基准仍取同一刷新批次的首次完整自动观测且当天不可改写；每日趋势观测仍取最新完整批次，手工记录维护本来源对应日，自动来源缺日保留空值。
- 断开来源保留当前最后成功快照，但不进入断开后的新组合历史；历史金额沿用当时汇率观察。
- 投资资金进出账本、Modified Dietz 口径、来源总额与持仓覆盖分层、已知 EVM 协议适配器边界保持不变。
- 不建立第二套视觉语言；UI 相关 Ticket 复用既有组件和运行时 Token，实施时按固定设计上游复核。

## Testing Decisions

测试边界已向所有者征询，发布时未收到答复，以下为建议方案而非已确认意见。后续反馈优先更新本节及受影响 Ticket。

- 优先现有浏览器与 HTTP 业务入口，覆盖登录、锁定、备份预演恢复、来源详情和命令菜单；复用既有所有者认证、恢复锁定、无凭证备份、SQLite 持久化和命令菜单测试。
- 正式日结另用独立 CLI 子进程，因为该入口的导入、退出码与调度契约不能由 Web 路由测试替代。
- 持久化使用临时 SQLite 走公开业务 API 的完整导出—恢复，验证真实外键、事务与历史事实，不读取所有者数据库或凭证。
- 性能以合成历史样例做前后对照，关注返回结果等价及工作量随规模变化；单次耗时与精确 SQL 数量只作诊断，不承诺未经测量的延迟指标。
- 不为每个新模块新增独立测试入口；能在既有高层场景验证时，不镜像内部函数实现。认证并发/过期使用 HTTP 入口及可控样例补足。
- 修改后按 Ticket 运行相关检查。全量构建或浏览器回归确有必要时在隔离产物目录/环境中执行，避免覆盖共享开发服务使用的构建产物。
- 原生脚本先用受控工具链验证调度和错误传播，实际原生产物加载单独报告；规格发布阶段不做构建或真实账户验收。

## Out of Scope

## Further Notes

**领域文档冲突：** 历史 ADR 0001 仍用“日初基准”，并描述每次成功价格/持仓刷新更新趋势；当前 CONTEXT 明确采用“当日基准”与完整统一刷新批次。本规格按当前领域契约保持行为，不静默覆盖 ADR，也不借优化修改资产语义。相关 Ticket 实施前需核对其现有测试与契约；若要改变业务定义，应另行决策并同步文档。

**证据时效：** 结论来自 2026-09-10 审查快照。工作区已有大量进行中改动；实施前重新核对当前代码、锁文件与运行环境，不能将本规格的候选文件列表当作允许覆盖其他改动的授权。

**待进一步验证：** 依赖公告实际暴露面、长历史的端到端时延/内存、键盘问题的浏览器复现、加载/空/错状态及响应式覆盖、生产包体积、外部 CI、日志与真实平台稳定性。尚无缺陷证据的项目只记录验证需求，不预置整改结论。
