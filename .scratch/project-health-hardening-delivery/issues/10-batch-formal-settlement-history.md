# 10: 正式日结历史批量读取

**What to build:** 所有者查看或导出正式日结历史时，来源和持仓证据批量读取，历史规模增长不会导致逐日追加子查询。

**Blocked by:** None (can start immediately)

**Status:** resolved

**Phase:** 本迭代处理
**Priority:** 中
**Parent:** 原项目健康度规格 · 06 — 按来源和日期限制历史读取并消除逐行子查询

**Approval:** 2026-09-10 所有者确认 16 个执行切片及阻塞关系；本次授权仅为发布 Ticket，未授权代码实施。

## 验收标准

- [ ] 通过既有业务读取入口得到全部正式日结及其来源/持仓证据，保持排序、日期、市场、币种、历史汇率、采集时间和完整性状态。
- [ ] 不再按每个日结单独读取子记录；批量读取在 30/365/3650 天样例中体现可解释的工作量改善。
- [ ] 历史查看和现有完整导出调用不被范围限制或分页静默截断；空历史和含缺口历史结果正确。
- [ ] 读取不修改不可变日结，也不补造漏采日期；前后业务事实等价。

## 依据与最小范围

审查的正式日结读取呈 2D+1 查询形态；实际端到端延迟尚未建立基线。

仅替换正式日结读取算法；03 负责新增备份数据域，本 Ticket 不以该扩展完成为前提，待其接入后复用同一完整读取能力。

## 验证方式

通过现有正式日结历史业务入口及临时 SQLite 完整读取验收，使用诊断查询计数和合成规模对比。

沿用现有最高业务入口。自动化样例、真实运行和未执行检查分别报告；审查快照不替代修改后验收。测试和恢复使用隔离数据，不能访问所有者凭证或破坏其业务库。

## 风险与收益

低至中；防止证据遗漏和重复组合，收益为减轻长日结历史读取。

只实现本 Ticket。保留既有未提交改动；实施前核对当前代码与领域契约，并给出最小变更文件清单。代码位置与函数证据在父级审查资料中查找，本 Ticket 不固定实现路径。
