# 资产刷新机制重设计

Status: proposed

Last verified: 2026-08-26

## 1. 目标

建立一套统一、低频、可解释的资产刷新机制：

- 资产已有最后成功数据时，刷新失败继续显示该金额，不降为零，也不误报成“数据不完整”；
- 将“数据是否完整”和“数据是否新鲜”拆成两个独立维度；
- 默认所有自动来源共用一个每小时完整刷新批次，取消逐来源到期以及行情与持仓的多套自动周期；
- 总览、资产与持仓、收益分析使用同一个刷新入口和状态；
- 保留来源详情页的单来源刷新，但由统一刷新模块执行；
- 修正当日基准、日内趋势、文档和 E2E 之间的冲突。

## 2. 当前实现事实

截至 2026-08-24，实际运行行为如下：

1. 总览页挂载 AssetRefreshControls，但明确传入 automaticRefresh={false}，所以只有手动全量刷新生效。
2. /assets 与 /performance 的命令菜单会广播手动刷新事件，但页面没有刷新监听器，点击不会调用刷新接口。
3. 服务端对不同刷新批次串行排队；同一批次内，各来源并行读取；生产环境每个来源独立超时 60 秒。
4. 来源失败时保留最后成功快照，更新最后尝试时间、错误和过期状态。
5. prices 保留持仓数量，只更新估值；生产使用的长桥 Keychain 刷新器会真实读取行情。遗留 OAuth 刷新器的 prices 才会直接返回旧快照。
6. 当前日级基准写入会接受不完整观测，且后续完整观测不能纠正已有的 incomplete 记录；目标方案将不再创建这种不完整基准。
7. 失败刷新会影响当日趋势观测状态，导致“有完整旧金额”和“本次刷新失败”被折叠成 expired 或界面上的“不完整”。
8. OwnerDashboard 没有当前路由引用；但 AssetSourceRefreshButton 仍由来源详情页的 AssetSourceCard 使用。

## 3. 产品语义

### 3.1 完整性与新鲜度必须分开

每份来源数据同时拥有两个状态：

| 维度 | 状态 | 含义 |
| --- | --- | --- |
| 完整性 | complete | 已知持仓均已读取，且需要纳入总额的资产均可估值 |
| 完整性 | incomplete | 存在漏读、未估值或缺失金额；总额本身不完整 |
| 新鲜度 | fresh | 最近一次完整刷新成功，且未超过一小时 |
| 新鲜度 | stale | 最近完整刷新失败，或距离最后成功刷新超过一小时；金额仍来自最后成功快照 |

允许出现四种组合：

- complete + fresh：完整且当前；
- complete + stale：金额完整，但使用旧数据；
- incomplete + fresh：刚刷新成功，但来源本身仍有未估值或覆盖缺口；
- incomplete + stale：既存在覆盖缺口，也没有新鲜数据。

关键规则：如果上午 10:00 已获得完整数据，11:00 刷新失败，则 10:00 的金额继续显示，完整性仍是 complete，新鲜度变成 stale。总资产继续正常展示，不显示为零，也不误报成“总额不完整”；失败状态和最后成功时间在来源级展示。

断开来源只改变连接生命周期，不代表该来源资产归零：其最后成功快照继续参与当前总资产汇总，快照原有完整性不因断开而改变；来源不再刷新，超过一小时后自然变为 stale。恢复连接成功后以新快照替换，只有永久删除来源数据才移除该来源的当前值和历史。

### 3.2 错误属于同步健康，不属于资产事实

- lastSuccessfulAt 表示当前金额来自何时；
- lastAttemptAt 表示最近何时尝试刷新；
- error 表示最近失败原因；
- 失败不得修改最后成功快照的金额、持仓数量、完整性或成功观测时间；
- 成功刷新才可以替换资产事实。

## 4. 智能刷新策略

自动刷新只有一种：所有已连接且具备只读凭证的自动来源共用一个每小时完整刷新批次，同时读取余额、持仓和估值。不再自动执行 prices-only 刷新，也不再为每个来源分别计算到期时间；刷新模块只为统一批次的下一执行时间设置单次定时器。

| 场景 | 行为 |
| --- | --- |
| 首次进入页面 | 从未形成统一周期锚点或距离上次全量尝试已满一小时，则刷新全部自动来源 |
| 旧版本升级后首次进入 | 已有自动来源但尚无统一周期锚点时，在页面可见且浏览器窗口获得焦点后执行一次全量刷新；不使用旧来源各自的刷新时间推算统一周期 |
| 首次连接第一个自动来源 | 直接使用确认连接时重新校验取得并保存的快照，以连接成功时间建立统一周期，不再追加一次刷新 |
| 新增或重新连接自动来源 | 保存本次重新校验取得的快照，不立即追加全量刷新，也不重置既有统一周期 |
| 页面重新可见或重新获得焦点 | 重新判断统一批次是否到期；未到期则不请求，失焦期间错过的周期只补一次判断 |
| 页面隐藏、标签页不在前台或浏览器窗口失焦 | 取消自动定时器且不发起自动请求；已在途请求允许按现有服务端规则结束 |
| 自动完整刷新 | 每个统一批次对全部自动来源执行一次 all/all |
| 自动刷新失败 | 不设置快速重试；整个批次等待一小时后再统一尝试 |
| 手动全量刷新 | 始终执行 all/all，并从本次尝试时间重新计算下一统一周期 |
| 手动单来源刷新 | 始终执行该 sourceId 的 all，不刷新其他来源，也不改变统一周期 |

补充约束：

- 自动刷新不拆分来源到期时间；同一统一批次始终读取全部自动来源；
- 自动批次只有在 `document.visibilityState === "visible"`、当前页面处于焦点且统一周期已满一小时三个条件同时成立时才允许启动；
- 页面可见但浏览器窗口失焦时不自动刷新；重新获得焦点后只重新判断一次，不补刷失焦期间错过的多个周期；
- 自动批次一旦已经开始，不因页面隐藏、标签切换或浏览器窗口失焦而取消；
- 首个自动来源连接成功时，以实际连接成功时间初始化 `asset_full_refresh_attempted_at`；只有连接事务成功后才写入，连接失败不能建立周期；
- 后续新增来源、恢复来源或更换授权材料时，不改写 `asset_full_refresh_attempted_at`；需要立即取得全部来源同一批次的数据时，由所有者手动全量刷新；
- 页面进入、定时检查、返回前台和命令菜单同时触发时，必须合并重复意图；
- 手动全量刷新后，以该次全量尝试时间重新计算下一小时周期；手动单来源刷新不改变该周期；
- 刷新失败后重新打开页面或返回前台，不能绕过上一全量批次尝试时间的一小时周期；
- 不在本次方案中增加“实时模式”。如后续确有 30 秒行情需求，应作为独立功能显式开启。

## 5. 统一刷新模块

### 5.1 模块与 seam

新增一个统一的 AssetRefreshCoordinator 模块，放在工作台 shell 与刷新接口之间。

它对页面只暴露以下 interface：

~~~ts
type AssetRefreshIntent =
  | { reason: "manual-global" }
  | { reason: "manual-source"; sourceId: string }
  | { reason: "page-entry" | "foreground" | "interval" };

interface AssetRefreshCoordinatorValue {
  request(intent: AssetRefreshIntent): Promise<void>;
  canRefresh: boolean;
  state: "idle" | "planning" | "refreshing" | "success" | "partial" | "error";
  message: string;
}
~~~

页面和按钮不再自行理解一小时周期、失败后的下次可尝试时间或并发规则。计划计算应为纯函数，输入上一全量批次时间、来源摘要、当前时间、页面可见性、页面焦点和意图，输出是否向服务端申请统一刷新批次及下一批次时间。客户端判断只用于减少无效请求，服务端才是统一周期和并发资格的最终判断者。

### 5.2 挂载位置

- 根布局挂载唯一的刷新 Provider，使其生命周期高于各页面分别创建的 WorkbenchShell；
- 总览、/assets、/performance 只向 Provider 注册可刷新来源摘要，不各自保存调度状态；
- 页面切换不销毁在途请求、刷新反馈或下一次到期计划，也不因重新挂载而重复刷新；
- 锁定、退出登录或进入演示模式时，Provider 清除来源计划并停止自动刷新；
- Provider 只保存来源 ID、同步时间、在途目标和刷新反馈，不保存资产金额；资产事实仍以服务端读取和页面重新渲染为准；
- canRefresh 由 Provider 根据“至少一个已连接且具备可用只读凭证的自动来源”统一计算，页面按钮和命令菜单不得分别推断；
- canRefresh=false 时不创建自动定时器、不提交刷新请求，并同时隐藏三个核心页面的刷新按钮和命令菜单“立即刷新资产”；
- 资产来源管理入口始终保留，供所有者新增来源、重新连接或修复凭证；来源恢复为可刷新后，Provider 重新计算计划并恢复统一刷新入口；
- WorkbenchShell 只承载刷新入口和状态展示，不理解一小时周期、请求合并或失败冷却规则；
- CommandMenu 直接调用 coordinator，不再广播浏览器自定义事件；
- 总览页“立即刷新资产”按钮消费同一个 coordinator 状态；
- 来源详情页的单来源刷新按钮也调用同一个 interface；
- 来源详情页只提供单来源刷新入口，不同时暴露全量刷新命令；
- 移除 pad:asset-manual-refresh 事件及重复监听器。

### 5.3 服务端批次

保留现有安全特性：

- 不同批次串行，避免并发写入互相覆盖；
- 同批次来源并行；
- 每个来源独立 60 秒超时；
- 一个来源失败不阻止其他来源提交；
- 失败保留最后成功快照。

为支持 coordinator 合并排队目标，刷新请求增加可选 sourceIds: string[]，并与 sourceId、scope 互斥。服务端必须校验所有目标均为已连接且有只读凭证的来源。自动统一批次仍使用 all/all；旧的 sourceId 与 scope 调用保持兼容。

超时和批次完成遵守以下合同：

- 实际批次开始时记录 fullBatchAttemptedAt；下一次自动到期时间始终为该时间 + 1 小时，不按批次结束时间顺延；
- 最近一次全量批次开始时间使用现有 `schema_metadata` 键值表持久化，固定键为 `asset_full_refresh_attempted_at`；批次进行中另使用 `asset_full_refresh_in_progress_at`，不新增表、字段或 schema 版本；
- 自动请求到达后，服务端在开始读取来源前原子判断一小时周期并预占全量批次；未到期时直接跳过，不能仅相信客户端传入的到期判断；
- 多标签或多个页面同时申请全量刷新时，服务端只允许一份全量批次进入来源读取；其余请求复用当前批次结果或返回已在途/已跳过结果，不能再次调用来源 Adapter；
- 手动全量允许绕过一小时时间限制，但仍必须服从同一份服务端在途批次保护；手动单来源不读写 `asset_full_refresh_attempted_at`；
- `asset_full_refresh_attempted_at` 与 `asset_full_refresh_in_progress_at` 在任何外部来源读取开始前原子提交，并写入同一个批次开始时间；服务端进程随后异常退出时，两项记录均保留；
- 同批次全部来源同时开始读取，每个来源分别在 60 秒后超时，因此多个慢来源不会把等待时间串行累加；
- 批次等待全部来源成功、失败或超时后结束，正常最长等待约 60 秒加少量收尾时间；
- 批次正常进入任一终态后，无论全部成功、部分失败还是全部失败，都清除 `asset_full_refresh_in_progress_at`；
- 已成功来源独立提交新快照；失败或超时来源保留最后成功快照，不因同批次其他来源失败而回滚；
- 服务端进程在批次中途退出时，退出前已经提交的成功来源快照继续保留，尚未完成的来源继续保留其最后成功快照，不能为恢复组合历史而回滚成功来源；
- 服务恢复后不为中断批次增加自动重试，仍按已持久化的批次开始时间 + 1 小时判断下一次自动刷新；所有者仍可随时手动全量刷新；
- 服务启动时若发现 `asset_full_refresh_in_progress_at` 仍存在，则将其解释为上次全量批次异常中断；该标记只用于诊断，不能作为跨进程活锁永久阻止后续到期刷新或手动全量刷新；
- 异常中断不改变总资产、来源快照或估值完整性，也不在总览持续显示警告；数据健康入口显示“上次刷新未完成”，下一份全量批次正常结束后清除该诊断；
- 任一必要来源失败或超时即为部分失败，不能写组合级当日基准或趋势；全部来源失败同样不写组合历史；
- 手动部分失败显示“部分来源刷新失败”，自动部分失败保持静默；两者均不快速重试，等待下一统一周期；
- 测试通过刷新执行器 interface 注入可控成功、失败和挂起 Adapter，配合假时钟验证批次结果、60 秒超时与下一到期时间，不断言内部 Promise 或计时器变量。

### 5.4 请求重叠与目标合并

- 全量批次进行中再次收到自动或手动全量意图时，后来的意图复用当前批次，不重复读取；
- 全量批次进行中收到单来源意图时，如果该来源已包含在当前批次中，则复用当前批次；
- 单来源 A 进行中再次收到 A 的单来源意图时，复用当前批次；收到 B 的单来源意图时，将 B 排入后续批次；
- 多个单来源目标排队期间收到全量意图时，未开始的零散队列由一份新的全量批次吸收，不再逐个执行；
- 单来源 A 已经开始后收到全量意图时，先让当前单来源批次结束，再执行一份包含 A 和所有其他自动来源的真正全量批次；允许 A 顺序读取两次，以保证组合历史只使用同一完整批次的数据；
- 同一来源不能并发读取；只有前述“单来源批次后接真正全量批次”的场景允许顺序再次读取；
- 页面进入、返回前台与定时到期同时触发时，只计算并执行一份刷新计划；
- 页面路由切换本身不触发重复请求，刷新状态和在途目标由 shell 上层的 coordinator 持有；
- 只有真正的全量批次可以写组合级每日历史；被复用或吸收的意图不能额外触发历史写入。

### 5.5 单来源刷新入口

- 来源详情保留“刷新”按钮，通过 coordinator 提交 manual-source 意图，只对当前 sourceId 执行 all；
- 手动单来源刷新不受一小时周期限制；
- 执行或排队期间显示“刷新中…”和“正在刷新…”；完成后显示“刷新完成”或“刷新失败”；
- 具体错误原因留在来源同步状态和数据健康页，不展开在按钮旁；
- 全量刷新已经包含当前来源时，单来源按钮禁用并复用当前在途请求；
- 其他来源正在自动刷新时，用户仍可请求当前来源，coordinator 将其加入后续目标；
- 离开来源详情页不取消请求，其他页面继续读取共享刷新状态；
- 单来源成功可以更新当前来源资产事实，但不能单独写入组合级每日历史。

### 5.6 页面数据重读

- 刷新期间继续显示现有服务端数据，不清空金额、不展示资产骨架屏，也不在浏览器中乐观修改金额；
- 每个实际服务端批次结束后只触发一次当前路由数据重读；同批次多个来源并行完成不能分别触发页面重读；
- 如果合并意图形成后续批次，则每个后续批次结束后各重读一次，使已成功来源不必等待所有排队目标完成才显示；
- 部分成功时，重读后显示成功来源的新快照与失败来源保留的旧快照；全部失败时也重读，以显示最新尝试时间和错误；
- 手动意图只有在它要求的全部目标处理完毕后才生成最终反馈，不能在中间批次提前显示完成；
- 请求期间切换页面时，批次结束后重读用户当时所在的当前路由；
- 自动刷新使用同样的数据重读机制，但完成后不显示成功提示。

### 5.7 所有者会话与演示模式切换

- 工作台锁定、退出登录或进入演示模式时，Provider 立即清除自动定时器、尚未开始的刷新意图、共享状态和反馈；
- 状态切换后不再发起真实来源请求；演示模式始终不能读取或展示真实资产刷新结果；
- 已经提交到服务端并开始执行的批次允许按原合同完成，因为客户端取消不能可靠回滚已开始的外部读取和数据库写入；
- Provider 与已开始批次脱离，不等待其结果、不显示完成反馈，也不在锁定、退出或演示页面触发路由数据重读；
- 再次解锁或登录后，从服务端重新读取来源与最近全量尝试时间，再按统一一小时规则规划；后台已完成的合法批次作为服务端事实正常生效；
- coordinator interface 测试验证未开始意图被清空且不再请求；浏览器回归验证锁定、退出和演示页面不显示真实刷新状态；服务端批次测试独立证明已开始任务仍可安全完成。

### 5.8 在途批次期间来源集合变化

- 每个批次在实际开始时固定本次目标来源集合；执行过程中新增、断开或修复来源时，不动态插入或移除在途目标；
- 外部读取已经开始后不强制中断，但每个来源的结果在保存前必须重新核对当前生命周期；仍保持连接的来源可独立保存可用的当前快照；
- 来源在读取期间被断开时，丢弃本次返回结果，保留断开前已有的来源身份、资产卡片与历史快照，不能用在途结果继续更新它；
- 来源在读取期间被永久删除时，丢弃本次返回结果，且不能重新创建来源、同步状态、当前快照或任何历史数据；
- 每次开始读取来源时，服务端同时捕获该来源的内部连接版本；连接版本只在服务端用于并发校验，不暴露凭证引用、公开地址或其他授权材料；
- 来源在读取期间更换授权材料、重新连接或恢复连接时，保存前发现连接版本已经变化，则丢弃旧请求结果，以重新校验并保存的新连接快照为准；旧结果不能覆盖新快照；
- 连接版本优先复用每次连接都会更换的现有不透明凭证引用作为比较依据；若具体 Adapter 不具备这种稳定身份，再由持久化 seam 提供等价的递增版本，不要求客户端参与判断；
- 因连接版本变化而被丢弃的旧结果记为内部 `superseded` 终态，不计入成功或失败，不改写该来源的快照、lastAttemptAt、lastSuccessfulAt 或 error；
- `superseded` 不产生来源错误或“刷新失败”反馈；手动批次没有真实失败时仍可正常结束，自动批次继续静默，但来源集合或连接版本变化后该批次仍不能写组合历史；
- 当前集合与批次开始集合不一致时，该批次不能建立或更新组合级当日基准及趋势，避免把不同来源口径写成同一条历史；
- 来源集合变化本身不自动追加全量批次，也不重置统一周期；下一次自动刷新仍按最近全量批次开始时间 + 1 小时执行；
- 如果此前没有任何自动来源，首个来源确认连接时已经保存重新校验后的当前快照，并以连接成功时间初始化统一周期，不再立即重复读取；
- 如果此前已经存在自动来源，新增、重新连接或恢复来源只保存本次来源快照，不改变既有周期；例如 A 在 10:00 建立周期、B 在 10:30 接入，则 10:30 不刷新 A，下一次统一自动刷新仍为 11:00；
- 最后一个可刷新自动来源被断开或删除后，统一周期不再有业务含义；若此时没有在途全量批次，立即清除 `asset_full_refresh_attempted_at` 与遗留的 `asset_full_refresh_in_progress_at`；
- 最后一个来源消失时若全量批次已经开始，不强行中断或提前清除进行中标记；批次按既有合同结束后，由服务端在确认当前仍无可刷新来源时清除两项周期记录；
- 之后重新连接的第一个自动来源按“首次来源”处理：直接使用连接时保存的重新校验快照，以本次连接成功时间重新建立一小时周期，不继承已经清除的旧周期；
- 用户需要立即取得最新来源集合的完整观测时，可以手动全量刷新，并由该手动批次重新计算统一周期；
- 短时间内多次来源配置变化不形成刷新队列；coordinator 只更新最新来源摘要和下一统一批次目标；
- 测试通过来源注册表 interface 在批次执行中切换目标集合和连接版本，验证仍连接且版本未变来源的当前快照可以保存、已断开或删除来源的返回结果被丢弃、旧连接结果以 `superseded` 结束且不能覆盖重新连接快照或污染失败统计、永久删除的数据不会复活、组合历史不写入、没有额外批次且下一周期不变。

### 5.9 页面重载、浏览器关闭与多标签

- 最近一次全量批次开始时间属于服务端持久化事实，使用 `schema_metadata.asset_full_refresh_attempted_at` 保存，不能只存在 Provider、浏览器内存或单个标签页；
- 从旧版本升级后，如果已有可刷新自动来源但 `asset_full_refresh_attempted_at` 尚不存在，则统一周期视为已到期；首次满足页面可见且浏览器窗口获得焦点时执行一次全量刷新，不根据旧版各来源的 `lastAttemptAt` 推算统一周期；
- 升级后页面未打开、处于隐藏状态或浏览器窗口未获得焦点时不执行后台刷新；首次全量刷新无论成功、部分失败或全部失败，都以实际批次开始时间建立新周期，后续等待一小时，不因页面重载快速重试；
- 页面刷新、路由切换、Provider 重新挂载和浏览器重启均从服务端恢复该时间，不重置统一一小时周期；
- 服务端进程在全量批次中途退出并重新启动时，同样从该时间恢复周期；不能因进程重启立即再启动一份自动全量批次；
- 遗留的 `asset_full_refresh_in_progress_at` 表示上一批次被中断，但不代表重启后仍有任务执行；到达下一周期或收到手动全量意图时，服务端可以开始新批次并覆盖该标记；
- 浏览器关闭期间没有客户端定时器、服务端 cron 或后台 worker，不会自行刷新；重新打开时仅判断是否已经到期；
- 例如 10:00 已开始全量批次，10:30 重新打开时不请求，11:00 后重新打开时立即请求；
- 手动单来源刷新不能改写该时间；手动全量和自动全量均以实际批次开始时间更新；
- 客户端可提前判断未到期以减少请求，但服务端必须再次判断，且以服务端持久化时间为准；
- 多个标签页共享同一服务端周期和服务端原子防重复保护；一个标签刚完成或正在执行全量批次时，其他标签不得再产生一份重复全量读取；
- 持久化 seam 测试验证时间在 coordinator 重建后仍有效；浏览器回归验证重载、关闭后重开和两个标签页不会绕过周期。

## 6. 统一来源同步状态

统一一小时完整刷新后，不再新增 prices 与 holdings 两套刷新通道。每个来源沿用一套同步状态：

~~~ts
interface AssetSourceRefreshState {
  lastAttemptAt: string | null;
  lastSuccessfulAt: string | null;
  error: string | null;
}
~~~

写入与调度规则：

- 每次自动或手动 all 都更新 lastAttemptAt；
- 成功才替换来源当前快照、更新 lastSuccessfulAt 并清空错误；
- 失败只更新 lastAttemptAt 与错误，保留最后成功金额、持仓和 lastSuccessfulAt；
- 自动或手动全量批次结束后，下一次自动刷新时间为该批次尝试时间 + 1 小时；
- 全量批次部分失败或全部失败也不增加专门重试计时器，仍等待下一统一周期；
- 手动单来源刷新只更新该来源状态，不改变下一次自动全量批次时间；
- 现有 prices 与 holdings 服务端模式为兼容既有调用保留，但统一刷新模块不使用它们执行自动刷新；
- sync.status 只表达同步新鲜度，不再作为总额估值完整性的来源。

## 7. 当日基准与日内趋势

### 7.1 当日基准

当日基准采用“首次可信观测形成后冻结”规则：

1. 只有同一刷新批次完整取得全部必要自动来源，且总额估值完整时，才允许建立当天基准；
2. 首次连接第一个自动来源时，确认连接阶段重新校验并保存的快照等同于当时全部自动来源的一次完整观测；仅当该快照总额估值完整时，才允许建立当天基准；
3. 当天第一份符合条件的观测形成基准后不再覆盖；
4. 已经存在其他自动来源时，新增、重新连接或恢复某一个来源只更新当前资产事实，不能单独建立或替换组合级基准；
5. 部分来源成功、全部来源失败或单纯沿用过期数据均不创建临时基准，也不替换已有基准；
6. 当天始终没有完整成功批次时，当天没有基准，不用其他日期或混合时间点的数据补造；
7. 已断开来源的最后成功快照仍可用于当前总资产展示，但不属于当前批次的有效来源集合，不能参与断开后的新基准；
8. 手工资产记录只更新每日趋势观测，不改写已经形成的当日基准。

### 7.2 日内趋势观测

- 全部来源失败：不改变来源当前资产事实，不写入趋势观测，只更新来源级同步健康状态；
- 部分来源成功：成功来源立即更新当前快照，失败来源保留最后成功快照，当前总资产按各来源最新成功金额重新汇总；
- 部分来源成功不得建立或更新组合级每日趋势观测，避免把不同时间点的来源金额拼成正式历史；
- 全部必要自动来源在同一批次成功：正常建立或更新当天最新完整趋势观测；
- 首次连接第一个自动来源且其重新校验快照完整：可以建立或更新当天趋势，因为该快照覆盖了当时全部自动来源；
- 后续新增、重新连接或恢复某一来源：只更新当前来源快照，不建立或更新组合级趋势；例如 A 为 10:00 快照、B 在 10:30 接入，当前总资产可以显示 A + B，但需等 11:00 的 A + B 完整统一批次后才能写入组合趋势；
- 来源断开后：最后成功快照继续参与当前总资产展示并保留断开前历史，但不参与断开后的新组合趋势；例如 A 在 10:30 断开，次日只有 B 完成统一批次时，当前总资产仍可显示 A 最后金额 + B 最新金额，但次日组合趋势不能把 A 的旧金额与 B 的新金额拼在一起；
- 手工资产记录仍按其明确记录日期更新来源观测，不改变自动来源必须来自完整成功批次的规则；
- 历史金额的完整性由写入时的资产事实决定，不能被后续网络错误改写。

正式日结模块不在本次改造范围内，不能用页面刷新观测替代交易所正式收盘证据。

## 8. 界面与反馈

统一使用现有 Vibe 组件和运行时 Token，不新增第二套视觉语言。

- 总览、资产与持仓、收益分析在各自 WorkbenchPageHeader 的操作区挂载同一个页面刷新入口模块；
- 默认按钮显示“立即刷新资产”，刷新期间显示“刷新中…”并禁用；
- 刷新属于次要操作，使用 outline 样式；收益页“新增资金记录”等页面主操作继续使用 primary 样式；
- 刷新状态静态显示在按钮附近，不使用浮动 Toast；
- 页面切换后，新页面刷新入口继续读取同一 coordinator 状态；快捷命令触发的反馈也显示在当前页面刷新入口；
- 刷新中：按钮显示“刷新中…”，状态只显示“正在刷新…”，不显示来源数量、来源名称或百分比；
- 手动全部成功：显示“刷新完成”，约 2.4 秒后收起；自动全部成功静默更新；
- 手动部分失败：显示“部分来源刷新失败”，几秒后收起；自动部分失败静默记录；
- 手动全部失败：显示“刷新失败”，几秒后收起；自动全部失败静默记录并等待下一小时周期；
- 旧连接结果被新连接取代时不显示失败、不写来源错误；若同批次没有其他真实失败，手动刷新按正常完成反馈，自动刷新保持静默；
- 刷新期间保留现有数据，页面可以继续浏览；
- 同步成功但存在未估值资产时，本次同步仍属于“刷新完成”，资产完整性另行表达；
- 部分失败时，成功来源更新，失败来源保留最后成功数据；当前总资产继续按各来源最新成功金额汇总；
- 全部失败且已有数据时，继续显示原有总资产；从未成功的来源显示“暂无数据”，不能按零资产计算，总资产标记为不完整；
- 失败来源显示最近尝试结果和最后成功时间；
- 已断开来源继续以最后成功快照参与当前总资产，不因断开制造资产骤降；来源卡片与详情明确显示“已断开”和最后成功时间，不在总额卡持续显示“含旧数据”警告；
- 总额卡不因失败隐藏金额，也不持续显示“含旧数据”警告；
- 当来源更新时间不一致时，总额卡不宣称一个统一的最新时间；
- 状态使用 role=status，错误摘要可被辅助技术读取；按钮保持现有 40px 可点击区域和键盘操作。

### 8.1 核心页面与快捷命令验收

- 总览、/assets、/performance 均在页面标题操作区显示同一个 outline 刷新入口；
- 三个页面的刷新按钮和命令菜单“立即刷新资产”都提交同一个 manual-global 意图，不保留第二套事件或请求路径；
- 在任一入口开始刷新后切换页面，不取消在途请求、不重置统一一小时周期，也不因新页面挂载而重复请求；
- 切换后的当前页面继续显示共享的“刷新中…”和“正在刷新…”状态；
- 每个实际服务端批次结束只重读用户当时所在的当前路由一次；
- 三个页面共享相同的手动结果反馈：全部成功为“刷新完成”，部分失败为“部分来源刷新失败”，全部失败为“刷新失败”；
- 自动批次成功、部分失败或全部失败都不显示浮动提示，结果只进入共享状态、来源同步状态和数据健康；
- 聚焦浏览器回归按三个页面参数化运行，分别验证页面按钮和命令菜单都只产生一份全量刷新请求；另设一条跨页面用例验证状态延续、请求不重复和当前路由单次重读。

### 8.2 来源详情单来源刷新验收

- 来源 A 的刷新按钮只提交 manual-source(A)，只读取 A 的余额、持仓和估值，不读取其他来源；
- 单来源刷新不受统一一小时周期限制，也不改变上一全量尝试时间和下一次全量到期时间；
- 单来源成功只更新 A 的当前快照和同步状态，不建立或更新组合级当日基准及趋势；
- A 刷新期间再次点击 A 时复用同一请求，不产生第二个并发或排队批次；
- 离开来源详情页不取消请求；切换后的当前页面继续从共享 coordinator 显示“正在刷新…”；
- 单来源手动成功显示“刷新完成”，失败显示“刷新失败”；失败保留 A 最后一次成功的数据和 lastSuccessfulAt；
- 全量批次已包含 A 时，A 的单来源意图复用全量批次，不额外读取；其他重叠情况继续遵守 5.4 的排队与全量吸收规则；
- 聚焦浏览器回归验证按钮状态、跨页面延续和反馈；coordinator interface 测试验证目标来源、请求复用与周期不变；数据库 seam 验证单来源刷新不写组合历史。

### 8.3 无可刷新来源

- 没有已连接且具备可用只读凭证的自动来源时，coordinator 对外返回 canRefresh=false；
- 总览、/assets、/performance 的页面刷新按钮和命令菜单刷新项同时隐藏，不显示一个注定无效的禁用操作；
- 页面进入、返回前台和定时检查均不创建计时器或请求刷新接口；
- 手工资产与现有历史仍正常展示，资产来源管理入口继续可用；
- 最后一个可刷新自动来源消失且当前没有在途全量批次时，服务端清除全量尝试时间和异常中断诊断；若批次已经开始，则在批次结束并确认仍无来源后清除；
- 后续新增或重新连接第一个自动来源时，canRefresh 变为 true，所有入口同步恢复，并以连接成功时间建立新的统一周期；
- coordinator interface 测试验证空目标不调度；聚焦浏览器回归验证页面入口和命令菜单同时隐藏、恢复。

## 11. 验收标准

- [ ] 已有完整数据后刷新失败，金额和 lastSuccessfulAt 不变，完整性仍为 complete，新鲜度变为 stale。
- [ ] incomplete 只用于真实漏读、未估值或覆盖缺口，不能代表网络失败。
- [ ] 只有同一批次完整取得全部必要自动来源时才建立当日基准；基准建立后当天不再覆盖。
- [ ] 首次连接第一个自动来源且连接快照完整时，可以形成当日基准与趋势；连接后不再追加一次重复刷新。
- [ ] 已存在其他自动来源时，新增、重新连接或恢复单个来源只更新当前数据，不写组合级基准或趋势。
- [ ] 部分来源成功时，成功来源当前快照更新、失败来源保留最后成功快照，当前总资产继续汇总。
- [ ] 部分成功和全部失败均不会建立或更新组合级每日趋势观测。
- [ ] 页面进入且统一批次未到期时不发送刷新请求。
- [ ] 所有自动来源共用一个每小时完整刷新批次；不自动执行 prices-only 刷新。
- [ ] 刷新模块只为下一统一批次设置单次定时器，不进行逐来源定时或固定频率本地轮询。
- [ ] 页面隐藏、标签不在前台或浏览器窗口失焦时不启动自动请求；重新可见且获得焦点后仅在统一批次到期时刷新全部自动来源。
- [ ] 已经开始的批次不因页面隐藏、标签切换或浏览器窗口失焦而取消。
- [ ] 自动刷新失败后不快速重试；页面重开或返回前台不能绕过上一全量尝试时间 + 1 小时。
- [ ] 手动全量刷新始终执行；手动单来源刷新只更新目标来源。
- [ ] 总览、/assets、/performance 的命令菜单都能触发同一刷新流程，并显示一致反馈。
- [ ] 三个核心页面的页面按钮与命令菜单均只提交一份 manual-global 意图；刷新中切换页面保持状态且不重复请求。
- [ ] 每个实际服务端批次结束只重读当时所在页面一次；手动结果反馈一致，自动结果保持静默。
- [ ] 定时器、返回前台和手动操作重叠时，不产生重复来源请求。
- [ ] 自动、手动全量和手动单来源意图重叠时，同一来源同时最多执行一次，且其余目标不会丢失。
- [ ] 单来源 A 已开始后出现全量意图时，批次顺序为 A、再 A + 其余全部来源；A 可顺序读取两次，但只有后一个全量批次可写组合历史。
- [ ] 同批次来源并行、跨批次串行、来源独立 60 秒超时和部分失败隔离保持不变。
- [ ] 来源超时不回滚同批次成功来源；批次结束为部分失败且不写组合历史。
- [ ] 多个来源并行超时时整批等待不串行累加；下一自动到期时间按批次开始时间 + 1 小时计算。
- [ ] 服务端在批次中途退出时，批次开始时间仍保留；已提交的成功来源不回滚，未完成来源保留旧数据，重启后不自动重试。
- [ ] 中断批次后的下一自动到期时间仍按原批次开始时间 + 1 小时计算，手动全量刷新仍可立即执行。
- [ ] 来源详情页单来源刷新继续可用；OwnerDashboard 删除后无引用、无类型错误。
- [ ] 单来源刷新只读取目标来源，不改变统一一小时周期，也不写组合级每日历史。
- [ ] 单来源重复点击和在途全量覆盖时复用请求；离开详情页不取消刷新，成功或失败反馈正确。
- [ ] 无可刷新自动来源时不创建计时器或网络请求，三个页面按钮与命令菜单刷新项同时隐藏。
- [ ] 最后一个可刷新自动来源消失后清除全量尝试时间和异常中断诊断；已有批次不强制中断，结束后确认仍无来源再清除。
- [ ] 后续重新连接第一个自动来源时，canRefresh 和全部入口同步恢复，以连接成功时间重新建立统一周期，不继承旧周期。
- [ ] 锁定、退出登录或进入演示模式时，取消未开始意图并停止调度，不显示真实来源状态或触发页面重读。
- [ ] 状态切换前已开始的服务端批次允许完成；重新认证后从服务端事实恢复，并重新判断统一周期。
- [ ] 在途批次期间来源集合变化时不修改已经发出的外部读取；仍连接来源的成功快照可保存，已断开来源保留旧数据，已删除来源不能被返回结果重新创建，且该批次不写组合历史。
- [ ] 来源读取期间更换授权材料、重新连接或恢复连接时，服务端通过内部连接版本丢弃旧请求结果，新连接快照不能被旧结果覆盖。
- [ ] 被新连接取代的旧结果以 `superseded` 结束，不计入失败、不改写来源同步状态，也不显示刷新错误。
- [ ] 来源集合变化不自动补充全量刷新、不重置统一周期；下一周期使用最新来源集合，手动全量仍可立即刷新。
- [ ] 首个自动来源连接成功后直接使用接入流程保存的快照，并以连接成功时间初始化统一周期，不产生第二次来源读取。
- [ ] 已有自动来源后新增、重新连接或恢复来源，只保存该来源的新快照，不改写统一周期，也不自动追加全量批次。
- [ ] 页面重载、浏览器重启和多标签共享服务端最近全量批次时间，不能重置或绕过统一一小时周期。
- [ ] 旧版本升级后已有自动来源但没有统一周期元数据时，首次在已认证、页面可见且浏览器窗口获得焦点的状态下执行一次全量刷新；不使用旧来源各自的刷新时间推算周期。
- [ ] 升级后的首次全量刷新失败也保存批次开始时间并等待一小时；页面隐藏、失焦、重载或重新打开不能触发快速重试，手动全量仍可立即执行。
- [ ] `asset_full_refresh_attempted_at` 与 `asset_full_refresh_in_progress_at` 持久化在现有 `schema_metadata` 中；客户端只减少无效请求，服务端原子判断周期并阻止多标签重复读取。
- [ ] 全量批次开始时原子写入进行中标记，正常进入任一终态时清除；服务重启后遗留标记被识别为“上次刷新未完成”。
- [ ] 异常中断只在数据健康中显示，不改变资产完整性、不在总览持续警告，也不会成为阻止下一到期批次或手动全量刷新的永久锁。
- [ ] 断开来源停止同步但继续按最后成功快照计入当前总资产，来源级显示“已断开”和最后成功时间；恢复后由新快照替换，永久删除后才移除当前值和历史。
- [ ] 断开来源保留断开前历史，但其最后成功快照不参与断开后的新组合基准或每日趋势观测；重新连接并进入完整统一批次后才恢复参与组合历史。
- [ ] 浏览器关闭期间不执行后台刷新；重新打开时只有已经到期才发起全量请求。
- [ ] 更新 e2e/refresh-stale-data.spec.ts：删除旧“登录后立即全量刷新”和 30 秒固定轮询合同，改为验证智能到期策略。
- [ ] 增加首页、/assets、/performance 三个页面的命令刷新回归。
- [ ] 增加“完整批次形成当日基准、部分失败不写组合历史、完整性与新鲜度正交”的数据库回归。
- [ ] pnpm typecheck、相关 Node 测试、聚焦 Playwright、pnpm build 与 git diff --check 通过。

## 12. 非目标

- 不新增页面关闭后仍运行的服务端 cron 或后台 worker；
- 不实现 30 秒“实时模式”；
- 不自动执行独立行情刷新；
- 不改变正式日结、现金流和收益计算的业务定义；
- 不删除来源定向刷新能力；
- 不在本次工作中调整来源适配器的资产覆盖范围。
